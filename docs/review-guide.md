## 3. 夜间自治抓到的 3 个 bug(都修了,值得看一眼修法)

1. **`stability.ts` 的 `argv[indexOf('--input')+1]`**:没传 `--input` 时 indexOf=-1,取到 `argv[0]`(node.exe 本体),把 PE 二进制当 JSON 读。修法:先判 `indexOf >= 0` 再取参。这是经典坑,任何 `arr[indexOf(x)+1]` 都要过一遍脑子。
2. **adapter stdin 无监听 EPIPE**:超时 SIGKILL 后管道可能报 error,无监听的 error 事件会炸掉整个 runner(不是单条 case)。修法:`child.stdin.on('error', () => {})`,结果以 exit code 为准。
3. **report 嵌套加粗**:`✅ **PASS**` 外再包 `**` 破坏渲染。修法:去掉外层包裹。已用已存数据重渲染,没有重跑评测。

## 4. review 时建议重点拷问的 5 个取舍

1. **error 不计入通过率分母**(`src/runner.ts` summarize):我认为"管线挂了"不是"质量下滑",两者混在一个数字里会互相污染。反方观点:error 多到一定程度就该算质量信号(可用性也是质量)。你怎么看?
2. **重试只包适配器、规则失败不重跑**:保证测的是被测系统的真实输出。但适配器偶发崩溃时,这条 case 直接 error 退场——可以辩论"适配器崩溃是否该记质量失败"。
3. **引用一致性 = 子集 + 非空**:期望数组本身是 any-of 语义(eval.ts 同款),所以不要求集合相等。若要更严,可以加"Top-1 材料必须被引用"。
4. **judge 与被测系统同款模型(glm-4-flash 裁判 glm-4-flash)**:裁判和学生同级,靠 rubric 锚定补。`LLME_JUDGE_MODEL` 一个变量就能换强模型,但换模型前先看幂等性数据说话。
5. **门禁 83.3% 判 PASS**:阈值 80% 允许 12 条里挂 2 条,而这次挂的 2 条是真缺陷。阈值定多严是个产品问题不是技术问题——严了 CI 天天红没人看,松了缺陷溜进去。数据现在有了,阈值可以随时调。

> 搭建通用 LLM 输出评测管线:规则断言 + LLM-as-judge 两级评测(rubric 校准样例锚定、temperature=0,20 次复评 0 漂移),为 RAG 问答系统补齐生成端质量数字,评测抓出"检索正确但生成退化"真缺陷;全程成本计量(12 用例约 1 分钱),CI 退出码门禁。

---

### 消化题答案(先自己答再看)

1. **规则断言失效模式**:脆、覆盖不了语义——措辞稍变就误杀("没有足够信息"换成"日志里没提到"就挂),且抓不住"每个词都对但整体是编造"的答案。**judge 失效模式**:贵、慢、会漂移(尺度不稳)、会说好话(偏宽松)、裁判与学生同款模型时有盲区。互补:规则当免费的守门员筛掉硬伤,judge 做语义层的忠实度/质量判断;规则漂移不了,judge 便宜不了——分层才能既要又要。
2. temperature=0 治的是**采样随机**(同一输入输出抖动);校准样例治的是**分布偏移**(rubric 文本理解因 prompt 而异,打分尺度系统性漂移)。前者是方差问题,后者是偏差问题。证据:20 次复评 0 漂移,说明两个手段叠加后稳定性达标。
3. 退出码让评测从"给人看的报告"变成"给机器看的门禁":CI 里评测红 = 合入被挡,质量标准从"人记得看"变成"机器强制执行";阈值则把"什么叫合格"显式化、可辩论、可调整——没有阈值,评测结果就没有判决力,只有参考价值。
